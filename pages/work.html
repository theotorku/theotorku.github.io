AI Infrastructure • 2025–2026 • Deployed · Autonomous

ProplanOS — Multi-Agent Runtime

The Anthropic-native runtime everything else in the portfolio sits on. Agents don't just respond to a prompt — they run on schedules, react to events, recover from failure, and leave an audit trail. Built so that "the AI did something" is never a mystery.

Problem Framing

Most "AI agent" demos are a single request-response loop dressed up as autonomy. The moment you need an agent to run unattended — on a schedule, triggered by a webhook, surviving a crash mid-task — the demo falls apart. I needed a runtime, not a prompt: something that could orchestrate many agents reliably, control cost, and produce evidence of every decision it made.

The harder requirement was governance. If agents are going to act on their own, a non-technical operator has to be able to trust them. That means reasoning has to be separable from execution, and every action has to be replayable after the fact.

System Architecture

Orchestration: Claude (Sonnet 4.6) as the planner, with execution handled by dedicated services rather than the model itself.
Triggers: A cron scheduler plus event-driven triggers, so missions can start on a timer or in response to external events.
Durability: A database-backed job queue using SELECT … FOR UPDATE SKIP LOCKED for safe concurrent workers, with mission replay persistence so any run can be reconstructed.
Observability & safety: Live mission streaming, an immutable audit log (token counts, cost, duration per session), and an SSRF guard on outbound fetches.
Stack: Python 3.12 / FastAPI, Supabase (Postgres with views and triggers), deployed across Vercel (frontend) and Railway (backend). 24 tests.

Key Tradeoffs

Accepted: Separating reasoning from execution is more moving parts than letting the model "just call tools." That cost buys auditability and a hard boundary on what an agent can actually do — worth it for anything running unattended.

Rejected: Letting agents execute code or hit the network directly. Convenient in a demo, indefensible in production. Every action goes through a controlled path that can be logged, cost-capped, and replayed.

Where It Stands

Deployed and autonomous — running on cron and event triggers with the durable queue live. It's the substrate the product work (RevOS, the agent services) builds on, which is the real test: infrastructure earns its keep by what it lets you ship next, not by its own metrics.

What I'd Do Differently

Commit to the Claude Agent SDK earlier instead of hand-rolling parts of the execution and approval-gate layer. Some of what I built is now offered as a standard primitive — a reminder that on a fast-moving platform, "build vs. adopt" is a decision you have to keep re-making, not make once.

Vertical SaaS · Beauty • 2025–2026 • Live

Marie AI — Beauty Operations Assistant

An AI assistant for beauty professionals, shipped to production at jmarie.beauty. Not a chatbot bolted onto a website — a daily operating companion: client context, follow-ups, scheduling, and a proactive agent that does work before being asked.

Problem Framing

Independent beauty professionals run a real business out of a phone: bookings, client relationships, follow-ups, marketing. Generic CRMs are too heavy and generic AI chat is too passive. The opportunity wasn't "add AI" — it was to make the software do the chasing, so the operator could stay with clients.

The constraint that shaped everything: the user is non-technical and busy. If the product needs a setup wizard or a manual, it's already lost.

System Architecture

Frontend: React 19 + Vite.
Backend: Node.js / Express.
Data: Supabase (Postgres) with row-level security on every table.
Intelligence: Claude API for chat, drafting, and the relationship intelligence layer; a proactive daily agent on node-cron that surfaces work each morning.
Integrations: Stripe (live billing), Google OAuth (calendar/Gmail), Slack, and ElevenLabs voice output.
Quality: 24 tests, a WCAG AA accessibility pass, and a deployed acquisition funnel (landing page + waitlist with a Slack ping on every signup).

Key Tradeoffs

Accepted: I reversed an earlier auth decision — moved off a webhook-based integration and restored Google OAuth — because the architecturally cleaner option created friction for a non-technical user. UX won over purity, on purpose.

Rejected: A heavyweight, configurable CRM. The whole bet is that opinionated defaults beat flexibility for this user. Every settings screen avoided is a user retained.

Where It Stands

Live in production with billing enabled and the acquisition funnel instrumented — the one product in the portfolio with real users touching it daily. The current focus is honest and unglamorous: driving and measuring signups, then a Next.js v2 rebuild for scale. Built is not the same as adopted, and I track the difference.

What I'd Do Differently

Instrument the funnel from the first day the landing page went up, not after. For a stretch the page was live but unmeasured — and an unmeasured funnel is just a hope. Measurement is a day-one feature, not a later one.

AI Product • 2026 • Shipped · Pilots

AIVE — AI Visibility Audit

As buyers start asking AI assistants for recommendations, "are we visible to AI?" becomes a real question with no answer. AIVE turns it into a number: a deterministic 0–100 Agent Business Index that scores how well AI systems can understand, retrieve, and recommend a business.

Problem Framing

SEO measured visibility to search engines. Nothing measured visibility to AI agents — the systems increasingly mediating what customers find and choose. Business owners feel the shift but have no instrument for it. The product insight: don't build another analytics dashboard, build a single decision-grade score with a clear path to improve it.

System Architecture

Crawl: Playwright (headless Chromium) captures the live site.
Extract: An LLM with structured outputs turns pages into a clean semantic profile of the business.
Score: A deterministic Agent Business Index across five dimensions — AI Understanding, Retrieval, Recommendation, Agent Readiness, and Semantic Authority — rolled into one 0–100 number.
Deliver: A React + Chakra UI dashboard and report; FastAPI backend; Supabase; deployed on Vercel + Railway.
Discipline: The scoring model (ABI v0.1.1) is version-frozen against a benchmark of 54 profiles — no changes without a formal review, so a score means the same thing tomorrow as today.

Key Tradeoffs

Accepted: Determinism over cleverness. The score has to be stable and explainable, so the scoring layer is deterministic even though the extraction uses an LLM. A metric you can't trust to be consistent isn't a metric.

Accepted (and flagged): Extraction uses OpenAI structured outputs — the only non-Anthropic component in the portfolio. It was the right tool at build time; standardizing it onto Anthropic structured outputs is a deliberate open decision, not an oversight.

Where It Stands

Shipped as a productized offer — a working audit plus a full sales kit, tiered as a pilot audit, a standard audit, and an audit-plus-roadmap engagement. The freshest and most sales-ready asset in the portfolio; the current job is converting it into the first paid pilots before it goes stale.

Agency SaaS • 2026 • Feature-complete · Pre-launch

ScopeAI — Proposal & SOW Generator

Agencies lose billable hours turning a client brief into a polished proposal. ScopeAI compresses that: brief in, branded proposal out in minutes — PDF, email delivery, shareable links, and conversion into a statement of work.

Problem Framing

Proposal writing is high-frequency, low-leverage work: every agency does it constantly, and every one does it slightly differently. The win isn't a better document editor — it's collapsing the time from "we should send something" to "it's in their inbox," without the output looking generated.

System Architecture

App: Next.js 16 + TypeScript.
Pipeline: An AI pipeline (Claude Sonnet 4.6) that extracts from the brief and generates a structured, branded proposal, with conversion into a SOW.
Delivery: React-PDF export, Resend for email with tracking, and tokenized shareable links.
Data & billing: Supabase (Postgres with row-level security), org-scoped logo/asset storage, and Stripe metered billing.
Quality: 25 tests, with a dedicated security and billing-correctness hardening pass (server actions, AI input handling, share-link tokens).

Key Tradeoffs

Accepted: I spent real time hardening billing metering and share-link tokens before launch rather than after. For a product that handles money and client documents, getting that wrong in front of users is far more expensive than the delay.

Rejected: Shipping the moment it was feature-complete. Which is also the honest risk below.

Where It Stands

Feature-complete and hardened — and still pre-launch. This is the most important thing I can tell you about it: the gap between "done" and "in front of customers" is the hardest distance in the portfolio, and I'd rather name it than dress it up. The next move is a production deploy and beta outreach to the first agencies, full stop.

What I'd Do Differently

Set the launch date before the feature list. "Feature-complete" is a seductive stopping point that feels like progress while producing zero learning. Customers teach you things tests can't — and you only get that lesson by shipping.

Multi-Agent Orchestration • 2026 • Verified · Pre-launch

RevOS — Revenue Operating System

Multi-agent orchestration for sales teams: lead generation and qualification agents running on a durable workflow engine, with cost controls and an audit trail. The enterprise-shaped expression of the same governance thesis behind ProplanOS.

Problem Framing

Sales automation is full of brittle, single-purpose bots. The thesis here is that the durable unit isn't a bigger agent — it's an orchestration layer where scoped agents (generation, qualification) run as steps in a recoverable workflow, with budgets and a record of every decision. Enterprise buyers don't want magic; they want predictability they can audit.

System Architecture

Agents: A Lead Generation agent and a Qualification agent, each scoped to one responsibility with clear input/output contracts.
Orchestration: LangGraph for agent flow, Temporal.io for durable, recoverable workflows.
State & control: PostgreSQL and Redis, with explicit cost controls and a complete audit trail.
Packaging: Docker, with a complete API and a scaffolded frontend.

Key Tradeoffs

Accepted: Decomposing by responsibility means more orchestration code and less of a single "one agent does everything" demo moment. In exchange, each agent can be tested, improved, and reasoned about in isolation.

Rejected: Fine-tuned models. Structured prompting with verified outputs cleared the bar; training infrastructure wasn't justified by the marginal quality it would add.

Where It Stands

Both agents are verified end-to-end against the live model API and the backend is complete; the frontend is scaffolded. It then went idle for weeks while live products took priority — so the honest status is "verified, pre-launch, and overdue for a revive-or-pause decision." Naming that is part of operating a portfolio: not every bet gets pushed at once, and pretending otherwise is how things quietly rot.

These five are a representative slice, not the whole portfolio — there's also work in AI marketing/creative generation, podcast production, home-services intelligence, inbox triage, and an agent control plane with a sandboxed execution layer.
