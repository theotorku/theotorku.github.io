Decision Log

Journey

A reverse-chronological record of real decisions building ProPlan Solutions. Not a resume — a window into how I think. Each entry captures the context, constraints, the choice made, and what I learned. The honest ones — reversed calls, things built but not yet shipped — are signal, not noise.

The Pattern

Across a portfolio of AI products, a consistent decision pattern emerges:

  • The smallest thing that feels magical over building the whole vision
  • Governance and auditability as a moat — reasoning separated from execution
  • Composable, deployable stacks (Python/FastAPI, React/Next.js, Supabase, Claude) over locked-in platforms
  • Vertical focus over horizontal platforms — depth where generic tools fail
  • Ship to learn — built is not the same as adopted, and I track the difference
Jun 2026

Built a Metric Where None Existed

Context

Buyers are starting to ask AI assistants for recommendations, but businesses have no way to know whether AI systems can even understand or surface them. SEO measures visibility to search engines; nothing measured visibility to agents. I had a working crawler-plus-extraction pipeline and had to decide what to make of it.

Constraints

A score is only useful if it's trustworthy and repeatable. An LLM in the loop makes that hard — same input, different output erodes confidence fast. And the buyer is a business owner, not an analyst: they want an answer, not a dashboard to interpret.

Decision

Build AIVE around a single deterministic Agent Business Index — a 0–100 score across five dimensions — and version-freeze the scoring model (v0.1.1) against a benchmark of 54 profiles. The extraction can use an LLM; the scoring cannot. Ship it as a productized audit with a fix roadmap, not a self-serve analytics tool.

Outcome

Shipped as a tiered offer with a full sales kit — the freshest, most sales-ready asset in the portfolio. The open work is conversion: turning the audit into the first paid pilots before it idles.

Insight

The product is the decision, not the data. A frozen, explainable number that someone can act on beats a richer dashboard they have to decode. Determinism is a feature you sell.

2026, ongoing

Chose Shipping Over Building

Context

Several products reached "feature-complete" — ScopeAI hardened with 25 tests, a creative engine with billing live — and then sat. The portfolio was accumulating quality without accumulating customers. A pattern I could name: feature-complete, no users.

Constraints

Building is comfortable and measurable; launching is uncomfortable and exposes you to rejection. One operator across many bets means attention is the scarce resource, and "polish the thing I've already built" always feels safer than "put it in front of someone."

Decision

Treat the gap between done and deployed as the real work. Set launch dates before feature lists. Pick one product at a time and push it to first paying users rather than advancing five toward an asymptote.

Outcome

Marie AI is live with an instrumented funnel; AIVE shipped as a real offer. Others (RevOS, ScopeAI) are explicitly flagged as pre-launch and queued for a revive-or-pause call rather than left to quietly rot.

Insight

"Feature-complete" is a seductive stopping point that produces zero learning. Customers teach you what tests can't — and the only way to get that lesson is to ship and risk being wrong in public.

Apr 2026

Reversed My Own Architecture for the User

Context

For Marie AI's authentication and integrations, I had moved to a webhook-based pipeline — cleaner separation, fewer direct dependencies. On paper it was the better architecture. In the hands of a non-technical beauty professional, it added friction at exactly the wrong moment: onboarding.

Constraints

The user runs a business from a phone and has no patience for setup. Every extra step in the connect-your-accounts flow is a user lost. Architectural elegance is invisible to them; friction is not.

Decision

Reverse the call. Restore Google OAuth, remove the webhook integration. Take the slightly messier architecture in exchange for a one-tap connection the user actually completes.

Outcome

A smoother onboarding path for the people the product is for, plus a WCAG AA accessibility pass in the same stretch. The "worse" architecture was the right product decision.

Insight

Architectural purity is a means, never the goal. When the cleaner design costs the user a step, the user wins. Being willing to reverse your own decision is a feature, not a failure.

2025–2026

Made the Runtime Autonomous — and Auditable

Context

To run agents unattended — on schedules, reacting to events, surviving crashes — I needed a real runtime, not a prompt loop. The temptation was to let the model call tools and execute directly: fastest path to a working demo.

Constraints

Autonomy without accountability is a liability. If a non-technical operator is going to trust agents acting on their own, every action has to be bounded, cost-controlled, and reconstructable after the fact. Demos don't have to answer "what exactly did it do, and why?" — production does.

Decision

Build ProplanOS with reasoning separated from execution: Claude plans, but actions run through controlled paths. Add a durable, DB-backed job queue (SKIP LOCKED), cron and event triggers, mission replay, an immutable audit log, and an SSRF guard. Governance as the foundation, not a later add-on.

Outcome

A deployed, autonomous runtime the rest of the portfolio builds on. The same thesis — auditable, policy-bound agents — became the differentiator for the enterprise-facing products (RevOS, DecisionOS).

Insight

In AI products, governance is the moat. Anyone can demo an agent; far fewer can hand a buyer an audit trail. Separating reasoning from execution is what makes autonomy defensible.

Apr 2026

Standardized on One Model Provider — With Exceptions

Context

A portfolio of ~20 products had drifted across model providers and versions. When the platform announced model retirements and a wave of new capabilities (structured outputs, longer context, an agent SDK), the cost of being scattered became concrete.

Constraints

Standardizing everything risks dogma — sometimes another tool genuinely is better for a specific job. But unmanaged drift means every product is its own migration, its own surprise when an API changes underneath it.

Decision

Make the portfolio Anthropic-native by default (Claude Sonnet 4.6), audit and upgrade every model string ahead of the retirement deadline, and allow deliberate, documented exceptions where a best-tool case holds — AIVE's OpenAI extraction being the explicit one.

Outcome

A consistent default that makes capability upgrades a portfolio-wide win instead of a per-project scramble — and a short, honest list of exceptions rather than silent drift.

Insight

Standardize the default, not the dogma. A clear convention with a few named exceptions beats both rigid uniformity and accidental sprawl. The exceptions are only safe because they're explicit.
